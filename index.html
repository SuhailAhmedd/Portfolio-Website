Batch ETL · serverless · AWS

        
Spotify ETL Pipeline on AWS


        
Problem

        
Playlist data from the Spotify API is nested JSON that changes weekly. The goal was an automated pipeline that extracts artist, album and song data from the Top 50 playlist and makes it available for SQL analysis without running any servers.


        
Architecture

        
    
          
  1. sourceSpotify API
    2. 
          
  2. extractLambda (Spotipy)EventBridge, weekly
    3. 
          
  3. landS3 raw / to_process
    4. 
          
  4. transformLambda (Pandas)S3 event trigger
    5. 
          
  5. storeS3 transformedalbum · artist · song
    6. 
          
  6. catalogGlue crawlers
    7. 
          
  7. queryAthena
    8. 
        


        
Engineering

        

          
Ingestion
An extract Lambda calls the Spotify API through the Spotipy library, packaged as a Lambda layer, and writes raw JSON to raw_data/to_process. EventBridge runs it on a cron schedule every Tuesday.

          
Transformation
A new file in to_process triggers a second Lambda that uses Pandas to split the payload into album, artist and song datasets, then moves the raw file to processed.

          
Schema handling
One Glue crawler per dataset infers the schema and keeps the Glue Data Catalog current as new files arrive.

          
Storage
A single S3 bucket split into raw (to_process, processed) and transformed zones, so every run is traceable back to its raw extract.

          
Orchestration
Event driven end to end: a schedule starts extraction, and the S3 event starts transformation.

          
Monitoring
Lambda runs log to CloudWatch.

        


        
Technology

        
  • Python
  • Spotipy
  • Pandas
  • AWS Lambda
  • S3
  • EventBridge
  • Glue
  • Athena
  • CloudWatch

Streaming · Kafka · AWS

        
Real-Time Stock Market Pipeline


        
Problem

        
Market data is only useful while it's fresh. This project builds the operational side of a streaming pipeline: moving stock market records through Kafka as events, landing them in cloud storage and keeping them queryable with SQL.


        
Architecture

        
    
          
  1. sourceStock market dataset
    2. 
          
  2. producePython producer
    3. 
          
  3. streamKafka on EC2topics
    4. 
          
  4. consumePython consumer
    5. 
          
  5. storeS3
    6. 
          
  6. catalogGlue crawler
    7. 
          
  7. queryAthena
    8. 
        


        
Engineering

        

          
Ingestion
A Kafka cluster runs on an EC2 instance. A Python producer publishes stock market records to Kafka topics as a stream of events.

          
Processing
A Python consumer reads from the topics, processes each record and writes it to S3.

          
Schema handling
A Glue crawler scans the S3 data and creates and updates tables in the Glue Data Catalog.

          
Storage
Raw and processed data are kept in S3.

          
Analytics
Athena queries the catalogued data directly in S3 with standard SQL.

Lakehouse · batch + streaming · Databricks

        
ShopStream Databricks Lakehouse


        
Problem

        
A simulated e-commerce business has historical orders in CSV files and a live feed of JSON order events. The source data has double-fired order lines, impossible quantities and inconsistent status casing. Both paths need to end in one governed set of tables and a sales dashboard people can trust.


        
Architecture

        
batch

        
    
          
  1. sourceRaw CSVsorders, customers, products
    2. 
          
  2. ingestCOPY INTO
    3. 
          
  3. bronzeDelta, as landed
    4. 
          
  4. silverCleaned, typed, deduped
    5. 
          
  5. goldAggregates
    6. 
          
  6. analyticsSales dashboard
    7. 
        

        
streaming

        
    
          
  1. sourceLive JSON events
    2. 
          
  2. ingestAuto Loader
    3. 
          
  3. bronzeStreaming table
    4. 
          
  4. pipelineLakeflow declarative
    5. 
          
  5. serveDaily revenue view
    6. 
        


        
Engineering

        

          
Ingestion
Historical CSVs load with idempotent COPY INTO, so re-runs never duplicate data. Live JSON events arrive through Auto Loader with a checkpoint: the first run loaded 29 files, the second picked up only the 31 new ones, 1,500 events with no duplicates.

          
Data quality
Silver removes 234 double-fired order lines with ROW_NUMBER(), drops 259 rows with non-positive quantity, normalizes status casing and casts types. 13,717 raw rows become 13,228 trusted rows.

          
Schema handling
Schema inference and merge on ingest, explicit casts in Silver, and Bronze kept untouched so the original records are always available.

          
Storage
Delta tables across Bronze, Silver and Gold, with Delta DML and time travel preserving an audit trail. 12 tables governed in Unity Catalog.

          
Orchestration
A Lakeflow Job chains bronze, silver and gold notebooks with task dependencies. A Lakeflow declarative pipeline turns the event stream into a daily revenue materialized view.

          
Analytics
Three Gold tables (daily revenue, category performance, customer lifetime value) feed a Databricks SQL dashboard, with a SQL file that recomputes every KPI to check it.

        


        
Technology

        
  • Databricks
  • Databricks SQL
  • PySpark Structured Streaming
  • Delta Lake
  • Auto Loader
  • Lakeflow Jobs
  • Lakeflow Declarative Pipelines
  • Unity Catalog
  • AI/BI dashboards
